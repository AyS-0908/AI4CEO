## 1. PROJECT INTRODUCTION


**1.1. SELF-ASSESSMENT TOOL** for SMBs
Value proposition is to enable SMBs to self-assess:
- Strategic risk — Is AI an existential threat to the business model?
- Process AI-eligibility — Which processes can realistically benefit from AI (value vs. feasibility)?


**1.2. OUTPUT:** 
- A scored diagnosis
- and AI-generated strategic report (Google Doc).


**1.3. CORE LOGIC:**
1_company → 2_mission → 2_mission_function → optional instance creation in 3_diag_strategy and/or ⚠️ 3_diag_process → detailed scoring is entered at process level in ⚠️ 3_diag_process → final report generation tracked in 4_mission_report.
User Story: As the director of an SME, I want to assess my company’s AI maturity and identify high-impact processes in order to make informed decisions on adoption and minimise my risks.
Key features:
- Strategic vulnerability assessment: Immediately identify whether AI poses a direct threat to your business model or represents a growth opportunity.
- Process-specific assessment: Measure the relevance of AI for each business function (e.g. finance, HR, sales) by quantifying the actual added value against technical feasibility.
- Automatic project prioritisation: Classify your projects as ‘Quick Wins’, ‘Strategic Priorities’ or ‘Projects to Defer’ using our recommendation engine, to avoid unprofitable investments.
- ‘Turnkey’ action plan: Receive an automatically generated strategic report, incorporating personalised recommendations and a clear roadmap for your teams.


**1.4. STRUCTURAL PRINCIPLE:**
- 2_mission = mission header only
- 2_mission_function = authoritative function scope per mission
- 3_diag_strategy = macro strategic diagnosis
- ⚠️ 3_diag_process = function-scoped detailed scoring engine

## 2. SHEETS PRESENTATION        


### CORE INVARIANTS:
- A. `2_mission_function` is the sole authoritative source of process-diagnosis scope.
- B. `⚠️ 3_diag_process` must be created/read/grouped by `id_mission_function`.
- C. Function scope must never be inferred from labels, merged text, or names.
- D. Criteria columns are identified by matching Row-2 headers against pattern `crit_\d+`. Their left-to-right order must exactly match `_scoring_criteria` row order. The script must discover crit columns dynamically (regex on Row 2), never hardcode a fixed count.
- E. All reads/writes use row-2 canonical headers, never display labels or hardcoded column indexes.

### CRITICAL CONSTRAINTS FOR AI-CODER


**1. Boolean strings:** `is_active`, `has_strategy_diag`, `has_process_diag`, `is_customized`, `is_deleted` → compare with `=== 'True'`, never truthy check.
**2. Crit columns are dynamic:** Regex `CRIT_PATTERN` on row-2 headers. Never hardcode count or positions.
**3. Scope key = `id_mission_function`:** For `⚠️ 3_diag_department` and `⚠️ 3_diag_process`. `id_mission` is not a physical column in these sheets.
**4. Deterministic IDs:** `{missionId}_{lib_id}` or `{missionFunctionId}_{lib_id}`. Enables idempotent re-runs via duplicate check.
**5. API key in PropertiesService only:** Never in sheets.
**6. Formula columns are read-only:** Script reads computed values, never writes to them.
**7. Row 1 = display labels, Row 2 = canonical headers:** All reads/writes use Row 2.
**8. `SCHEMA` is documentation, not a framework:** Use it to validate field names in write calls. Do not build generic ORM/CRUD logic from it.
**9. `json_template` in `_settings_outputs` is legacy**. `buildJsonMission` output structure is authoritative.
**10. `compactRow`:** Must be applied AFTER grouping by `id_mission_function`, not before.
