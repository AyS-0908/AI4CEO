# SPECIFICATION — AI CONSULTANT


## 1. PROJECT OVERVIEW


**Product name**
AI Consultant


**Product objective**
Create a Google Sheets-based consulting toolkit that enables consultants to generate, structure, analyze, and export assignment-specific working assets using AI.
## 1.1 User Story
**The Goal:** As a consultant, I want to use my familiar spreadsheet environment to automate repetitive document creation and complex analysis, allowing me to focus on high-value insights.


**Concrete Workflow:**
* **Access:** Open your Google Sheet and select a tool from the custom 'AI Consultant' menu.
* **Input:** Provide assignment context (e.g., client name, project type) via a simple pop-up dialog.
* **Execute:** The AI generates structured data or deep analysis directly into your spreadsheet tabs.
* **Export:** Click to push refined insights and content into Google Docs, Slides, or Forms templates.


**Key User Features:**
* **Commercial Proposals:** Rapidly draft client-ready proposals and frameworks.
* **Market Benchmarking:** Run automated web research on industry players and data points.
* **Interview Management:** Structure interview guides and synthesize qualitative feedback.
* **Automated Exports:** Seamlessly populate professional document and slide templates.
* **Strategic Synthesis:** Analyze project data to surface insights and dashboards.




**Core constraint**
The product must operate inside the user’s existing Google Workspace workflow.


Google Sheets is:
- the main UI entry point
- the workflow orchestrator
- the source of truth for editable structured data


**Primary users**
Consultants working on client assignments in Google Workspace.


**MVP delivery mode**
MVP is a **Google Sheets bound script**.


**Rule:**
- Do not assume Google Marketplace add-on installation in MVP
- Code structure must allow later packaging as a Google Sheets add-on with minimal refactoring


**Architecture requirement**
The MVP must be config-driven and extensible so that new tools, dialogs, templates, and AI providers can be added with limited code changes.

## 2. MVP SCOPE


**In scope**
- Custom menu in Google Sheets
- HTML dialogs for user inputs
- Tool generation into Google Sheets tabs
- AI providers calls through user-provided API keys
- Export from Sheets to Google Docs, Google Slides, or Google Forms when supported by a tool
- Config-driven registries
- Optional developer-side feature/license activation registry


**Out of scope**
- Bidirectional sync between Sheets and generated Docs / Slides / Forms
- Auto-generated templates when no predefined template exists
- Complex multi-user workflow orchestration
- Marketplace publication constraints
- Advanced billing system
- End-user definition of arbitrary execution logic


---


## 3. CORE PRINCIPLES


**CP-1. Sheets-first**
Google Sheets is the only required operating surface in MVP.


**CP-2. Config-driven behavior**
Tools, actions, dialogs, schemas, and templates must be defined by registries, not hardcoded case-by-case.


**CP-3. Reusable execution pipelines**
When feasible and relevant, the same execution engine must support multiple tools through configuration.


**CP-4. One-way export**
Exports flow from Sheets to generated artifacts only.


**CP-5. Controlled extensibility**
Users may extend selected config areas only where validation exists.


**CP-6. Minimal add-on rework**
Core code must already separate UI, orchestration, providers, storage access, exports, and config validation.

## 6. PRIMARY WORKFLOW


**W1. Workbook initialization**
When the workbook opens, the script must execute via the `onOpen(e)` simple trigger to:
1. bind to the active spreadsheet
2. add the custom menu using `SpreadsheetApp.getUi().createMenu()`
3. verify required bootstrap sheets exist
4. create missing bootstrap sheets if allowed by config
5. validate critical configuration needed for menu/action availability


**W2. User action flow**
1. User selects a menu action
2. Script resolves `action_id`
3. Script loads the corresponding action definition
4. If a dialog is required, script renders the dialog from registry
5. User submits input
6. Script validates input
7. Script executes the mapped pipeline
8. Script writes results to target tabs and/or export artifacts
9. Script returns explicit success or error status


**UI Notification Rules:**
During pipeline execution, the UI must strictly show:
- A single start message (e.g., "✨ AI is working for you… It can take up to 2 mn").
- A final success message referencing the target output (e.g., "✅ Success -> See in [tab_name]") or an explicit error message.
- No real-time progress logs or granular status indicators are allowed.


**W3. Manual edits**
User may manually edit generated sheet content after generation.
Rule:
- Manual edits in Sheets are allowed
- Generated external artifacts are not required to sync back to Sheets

## 8. EXECUTION PIPELINES


### P1. Sheet generation pipeline
Used for tool creation or update (action: `tool_generate`).


Steps:
1. load tool config
2. load action config
3. collect dialog inputs if applicable
4. load referenced sheet schemas / prompt templates / dependencies
5. build AI request if applicable
6. call selected provider if applicable
7. create or update target tabs
8. write structured outputs


### P2. Aggregate analysis pipeline
Used when existing tabs or response data must be analyzed (action: `tool_analyze`).


Steps:
1. load source tabs / ranges / schema references
2. normalize source data
3. build analysis request
4. call provider
5. write structured outputs to analysis tabs


### P3. Document export pipeline
Used for Google Docs/Slides/Sheets export (action: `tool_export_*`). -- NOT for Form export (action `tool_export_form`).


Steps:
1. load template definition
2. collect export inputs
3. duplicate template
4. map placeholders from Sheets
5. save to destination folder


### P4. Form export pipeline
Used for Google Forms export.


Steps:
1. load questionnaire sheet schema
2. read current question definitions from Sheets
3. create form structure
4. link responses to workbook
5. register output metadata


### P5. Pipeline Execution Constraints


**Output Write Modes**
To support idempotence and iterative generation, pipelines writing to Sheets must dynamically support registry-defined write modes:
- `overwrite`: clear target range/body before writing (e.g., `clearAndWrite()`).
- `append`: insert output at the end of the existing content without altering manual notes.
- `replace_after_marker`: locate a specific text separator (e.g., `---MERGED---`) and overwrite only the content following it, preserving raw manual inputs above it.


**Batch Processing Limits**
For actions requiring looped provider calls (e.g., matrix of Questions × Players):
- The pipeline must calculate the total projected API calls before execution.
- If total calls > configured threshold (e.g., 50), the UI must display a warning dialog requiring explicit user confirmation before proceeding.




### P6. Context Injection Rules
Used by pipelines during the "build AI request" or "map placeholders" steps to merge dynamic workbook data into templates.


Rules for the AI Coder:
- All dynamic placeholders in prompt templates or document templates must use the double curly brace syntax: `{{VARIABLE_NAME}}`.
- The engine must parse the assigned schema or source tab and replace placeholders before executing the LLM call or document export.


Examples of standardized injection points based on tool configuration:
- `{{ASSIGNMENT_CONTEXT}}`: Concatenated string of the Client Context variables.
- `{{NOTES_CONTENT}}`: Raw data or notes retrieved from a specified source tab.
- `{{SYNTHESIS_TEMPLATE}}`: The structural body of a framework retrieved from the config.
- `{{PLAYER}}` / `{{QUESTION}}`: Specific iterative variables used during Benchmark or Data Insights execution loops.

| provider_settings | sheet metadata | Secure storage. Keys not visible in cells. |


**The Config.js File Contract**


Purpose:
To completely decouple business configuration from execution logic, allowing AI-assisted generation without risking engine stability.


Rules:
- All authoritative registries (`action_registry`, `dialog_registry`, `tool_registry`, `provider_registry`, `sheet_schema_registry`) must be consolidated into a single, dedicated Apps Script file named `config.js`.
- This file must contain **zero execution logic**, no functions, and no method calls.
- It must consist entirely of standard JavaScript object literals (JSON-like structure) assigned to global `const` variables.
- The W1 Initialization module and all Execution Pipelines must strictly read from these global constants.

## 14. PROVIDER RULES


**Provider selection**
Provider selection is:
- global by default at workbook level
- optionally overridable per action in later versions
- not per-task configurable in MVP unless explicitly enabled by code config


**API key storage**
API keys must be stored in Script Properties (`PropertiesService.getScriptProperties()`) using standard naming conventions (e.g., `API_KEY_OPENAI`, `API_KEY_GEMINI`).
Do not:
- store API keys in visible sheet cells
- duplicate API keys across tabs
- expose full keys in dialogs after save (UI must display partially hidden pre-filled values, e.g., `sk-...xxx`)
If a required key is missing when an action triggers, the script must throw an explicit error prompting the user to update their API Settings.


**Provider Adapter Interface**
To ensure reusable execution pipelines, all provider implementations (OpenAI, Google, Anthropic, Mistral, Perplexity) must implement a standardized adapter interface.


**Required Normalization:**


- **Input:** Pipelines must pass a unified `AIRequest` object to the provider adapter containing:
  - `system_prompt` (string)
  - `user_prompt` (string)
  - `temperature_optional` (number)
  - `response_format_optional` (enum: text, json_object)
  - `use_grounding_optional` (boolean) // Required for web search/benchmarking capabilities


- **Output:** The provider adapter must return a unified `AIResponse` object to the pipeline containing:
  - `content` (string or parsed JSON object)
  - `usage_metrics` (tokens used)
  - `status` (success | error)

## 17. SCALABILITY MODEL


**Goal**
- Allow developers to add new tools, dialogs, tabs, and templates with minimal code changes.
- Allow users to extend selected configuration areas safely, without editing core code.


**Design rule**
Scalability must come from:
- stable core engine
- declarative registries
- validated user extensions


Not from:
- spreadsheet formula tricks
- free-form JSON inside cells
- arbitrary user-entered formulas
- named-range-first architecture


---


## 18. SCALABILITY RULES


### SC-1. Stable core engine
Core modules:
- menu builder
- dialog renderer
- input validator
- pipeline executor
- provider adapter
- sheet writer
- export adapter
- config validator




### SC-2. Registry-driven extensibility
New tools must be added primarily through registry entries, not through custom branching in core code. 


**Adding new tool, action, or dialog :** 
Append the JSON object to the respective constant in the `config.js` ->  Core engine (`pipeline executor`, `dialog renderer`, etc.) dynamically adapt without logic updates.




### SC-3. Controlled user extensibility
In MVP, users may extend only selected config areas:
- `datalists`
- template mappings where overrides are allowed
- selected sheet/tab definitions only if explicitly enabled


Users must not alter:
- execution engine behavior
- provider adapters
- security logic
- unrestricted formulas


### SC-4. Validation timing
Validation must occur:
- on workbook initialization for critical registries
- before execution of any action using user-editable config
- when saving config changes through product UI, if such UI exists


### SC-5. Validation rules
Validation must check:
- required columns present
- unique IDs
- allowed enums
- valid references
- valid template source types
- valid formula preset references
- no forbidden values in user-editable config


If validation fails:
- stop only the impacted action when possible
- return explicit user-readable error


### SC-6. Formula model
Do not allow arbitrary formulas as core configuration.


Supported modes:
1. `formula_preset_id`
2. `literal_formula` for developer-managed config only


Preferred MVP mode:
- `formula_preset_id`


Example preset types:
- `concat_name`
- `completion_ratio`
- `weighted_score`
- `date_diff_days`


### SC-7. Field addressing model
Do not use one named range per field as the primary architecture.


Preferred model:
- registry-driven field IDs
- script-managed column mapping
- optional named ranges only for a limited number of stable anchors


### SC-8. Separation of concerns
Keep separate:
1. bootstrap/config sheets
2. runtime working tabs
3. export templates
4. provider settings
5. user business data


### SC-9. Standardized File Architecture 
**Goal:** 
Prevent the AI from combining separate concerns into a single file and ensure the "stable core engine" rule is physically represented in the codebase. 


**Required File Tree:** 
- `config.gs` (Contains ONLY the config.js constant objects) 
- `main.gs` (Contains entry points, triggers, and menu builders)

## 20. MARKDOWN TO DOCS CONVERSION


**Context**
Used primarily by the Document export pipeline during the `tool_export_doc` action to format LLM-generated content natively within a Google Doc template.


**Mapping Rules**
The conversion logic must strictly adhere to the following mapping using Apps Script `DocumentApp` methods:


| Markdown | Google Docs |
|---|---|
| `# Title` | Paragraph with `TITLE` style |
| `## Title` | Paragraph with `HEADING1` style |
| `### Title` | Paragraph in `HEADING2` style |
| `**text**` | `setBold(true)` on the text segment |
| `*text*` or `_text_` | `setItalic(true)` on the text segment |
| `1. element` | Native numbered list (`ListPreset.NUMBER`) |
| `- item` or `* item` | Native bulleted list (`ListPreset.BULLET`) |
| `  - sub-element` (2 spaces indentation) | Nested bulleted list (max 1 level depth) |
| Markdown table | Native Google Docs table |
| Plain text | `NORMAL` style paragraph |


**Constraints (MVP Scope)**
- **Out of scope:** Images, clickable links, code blocks, nested lists > 1 level, strikethrough, footnotes. 
- **Fallback:** Unrecognized Markdown syntax must be inserted as literal plain text.
- **Inline Combinations:** Bold and italics may appear within lists and table cells. The converter must treat them as inline formatting regardless of the block context.

## 23. MVP RISKS AND MITIGATIONS


**Objective**
Identify and mitigate technical and workflow risks specific to Google Apps Script and LLM orchestration to guide the coding implementation.


| Risk | Probability | Impact | Mitigation |
|---|---|---|---|
| 60-second timeout on LLM (long synthesis, data insights) | Medium | Workflow fails | - Implement execution monitoring.<br>- Breakdown tasks into sub-calls for MVP where possible. |
| `UrlFetchApp` quota (N×M data insights) | Low | Day-long blockage | - Implement a hard stop if > 50 calls.<br>- Ask user to reduce the number of questions or players before restarting. |
| Missing template | Low | Crash | - Require template verification upfront before pipeline execution.<br>- Return clear error messages. |
| Overwrites previous output | By design | Loss of previous version | - Include a clear confirmation message before execution.<br>- Rely on Google Sheets version history for recovery. |
| Grounding not supported by the provider configured | Low | Search without web sources | - Throw explicit error on API call failure.<br>- Inform the user they must choose a compatible provider (e.g., Gemini, Perplexity) for web-dependent actions. |

### ABOUT GOOGLE SLIDES GENERATION
**Objective** Enable users to select text in Google Slides and generate **editable business visuals** (flows, matrices, charts).
**Approach**
- Build a **Google Slides add-on (Apps Script)** reading selected text
- User chooses a **template type** (e.g., flow, 2x2, timeline, org chart, chart)
- LLM converts text → **strict JSON schema** matching the template
- Validate schema (constraints: steps count, structure, labels)
- Renderer maps schema → **native Slides objects** (shapes, connectors, tables, Sheets charts)
- Insert and **group elements** on the current slide
- Ensure **editability** (no images)
- Support **regenerate / switch template** from same input
- MVP scope: 4–6 templates, single text box, simple layouts
- V2: style options, multi-block parsing, auto template suggestion
